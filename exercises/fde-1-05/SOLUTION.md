# FDE 1.05 Reference solution

Released after the attempt window. One defensible scope:

## v1 — four items, in ship order

1. **Item 1 — reconcile and publish one signed returns answer.**
   The hypothesis cannot be tested until the disagreement that
   causes the second-source check is removed. Owner: operations
   manager, inside her stated condition (one answer, not the full
   policy document).
2. **Item 2 — one checked answer path for returns questions in the
   tool agents already use.** This is the intervention the FDE 1.04
   hypothesis names. Deliberately not automation: a checked path
   agents follow, so the four-week falsifier measures the removed
   check, not a new system's learning curve.
3. **Item 7 — log the walk-up queue in the ticket system.** In v1
   not because it is small but because it protects the measurement:
   118 unrecorded tickets in the discovery week is a hole in the
   baseline the falsifier will be checked against, and the senior
   agent — the person whose cooperation the count depends on —
   asked for it herself.
4. **Item 6, measurement slice only — hand-corrected categories for
   the falsifier sample weeks.** Not the full taxonomy fix: only
   the counting correction discovery already used, applied to the
   two sample weeks the falsifier needs, so the before and after
   counts are comparable. The full re-file is cut (see below).

## Not in v1 — the ten cuts

- **Item 3, chatbot (evidence):** the hypothesis has not been tested
  in its cheapest form; a chatbot automates an answer nobody has
  reconciled yet. Reconsider when the falsifier check passes.
- **Item 4, five-minute auto-replies (value):** first-response time
  is not the hypothesised cost; effort per returns question is. An
  instant holding reply moves the clock metric, not the work.
  Reconsider if the board asks for response time as its own target.
- **Item 5, tracking page (value):** a real workflow, but a
  different one — it does not test this hypothesis and it spends
  the window. Reconsider as the next engagement's framing candidate.
- **Item 6, full taxonomy fix (dependency):** only its measurement
  slice is a prerequisite; the full re-file is weeks of work the
  test does not need. Reconsider after the board number lands.
- **Item 8, board dashboard (dependency):** a dashboard built before
  the test reports counts, not a delta; the board gets the falsifier
  result as a one-page readout instead. Reconsider once there is a
  measured delta worth charting over time.
- **Item 9, sentiment routing (evidence):** no baseline, no owner,
  no hypothesis connects ticket mood to the measured cost.
  Reconsider only with a framed hypothesis of its own.
- **Item 10, warehouse integration (dependency):** the vendor lead
  time is eight weeks against a three-week window; it is not
  refused, it is impossible in this scope. Reconsider as the first
  item of a follow-on engagement, filed now so the clock starts.
- **Item 11, help-centre translation (value):** no discovery
  evidence links language to the measured returns-question cost.
  Reconsider with ticket data by customer language, if it exists.
- **Item 12, mobile support app (value):** a new channel adds volume
  surface before the existing workflow is fixed. Reconsider after
  v1's workflow holds at current volume.
- **Item 13, cost per ticket (dependency):** worth doing, starts
  week two at the earliest, and the hypothesis is about effort, not
  dollars — it runs parallel under Finance's ownership, outside v1,
  and must not gate the test. Reconsider as a v1 item only if the
  board makes dollars, not effort, the required number.
- **Item 14, ticket-tool replacement (ownership):** a procurement
  decision the sponsor cannot sign in this engagement; scoping it
  would promise what the room cannot deliver. Reconsider through
  procurement, on its own clock.

## The pushback paragraph (to the sponsor, on item 3)

"You asked for a chatbot that answers everything, and the instinct
is right — returns questions alone are 31% of everything support
handles. We are not building it in v1 for one stated reason: today
there is no single correct returns answer to automate, because the
policy page and the warehouse disagree, and a chatbot would give
the wrong window faster and at scale. v1 reconciles that answer,
proves in four weeks whether removing the disagreement cuts the
work, and gives you a measured number for the board. If the test
passes, the chatbot becomes the first item we scope next — built
on an answer we know is right."

## The engagement that cannot succeed

If the operations manager will not sign the one reconciled returns
answer, v1 should not start: items 1 and 2 are the hypothesis test,
and without the signature there is no test, only activity. The
recommendation instead is a one-week ownership escalation through
the sponsor — the disagreement is between two of the customer's own
documents, and no outside build resolves it — and, if the signature
still does not come, closing the engagement with the discovery
findings as the deliverable rather than spending the window on
items that cannot move the number.
