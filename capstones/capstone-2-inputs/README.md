# Capstone 2 — Provided inputs (all fictional, all synthetic)

The customer is Alder Creek Health Network, the fictional
regional health network used across the Phase 2 exercises.
Every file here was generated for this course; no real patient
data exists in this pack, and every patient reference is a
synthetic identifier invented by the generator.

| File | What it is |
|---|---|
| `clinician-notes.csv` | 1,200 clinician notes as exported from the legacy record system — not cleaned |
| `ehr-drop.csv` | The scheduled file-drop stand-in: 800 discharge records, semicolon-delimited, dates as DD/MM/YYYY |
| `drop-manifest.txt` | The manifest that arrived with the drop. It does not agree with the file |
| `security-questionnaire.md` | The network's security questionnaire, blank. Your answers need evidence artefacts, not adjectives |
| `data-handling-policy.md` | The network's data-handling policy, as issued to suppliers. Your build is judged against it |
| `phi-leak-injection.md` | The change injection. Sealed: open it only when your attempt reaches the incident drill — opening it early is reading the exam's second half first |

## What is wrong with the data (the shape, not the map)

You are told the shape of the mess, because an FDE is told the
shape by the customer. Finding the instances is the work:

- `clinician-notes.csv` carries **exact duplicates under
  different note ids** (about 3% of rows), **silently empty
  fields** (note text missing on some rows, patient reference
  missing on others), and **ward names in eight raw spellings
  for four wards**.
- Some notes carry the **patient reference inside the note
  text itself**. Under the data-handling policy that text is
  the most sensitive field in the pack: any system that logs,
  copies, or transmits note text carries the identifier with
  it. Finding every such row is part of the audit.
- `ehr-drop.csv` disagrees with its own manifest on the
  record count. Reconcile the drop before you build on it:
  state what was delivered, what the manifest claims, and
  what explains the difference — with counts, not impressions.
- The drop's empty discharge dates and empty diagnosis codes
  are silent: nothing marks them, the export simply omits
  the value.

Your data audit (the FDE 2.01 method, at capstone scale)
starts here: report the counts you find for each defect class
before you build anything on this data. A drafting workflow
built on the raw export inherits all of it.

## Generation note

Both datasets were generated by a seeded script (seed
20261127) so the data is identical for every learner and
every defect count in the reference solution is reproducible.
Note texts are drawn from fixed templates; the realism target
is the *structure* of a merged legacy export and a legacy
file drop, not literary variety. No real names, addresses, or
dates of birth appear anywhere in this pack — patient
references are synthetic identifiers of the form AC- followed
by digits, invented by the generator.
